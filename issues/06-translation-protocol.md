# 06: 翻译输出协议与 prompt 结构定案

Type: grilling
Status: resolved
Blocked by: 03

## Question

基于工单 03 的调研,与用户 grilling 定案:块粒度、LLM 输出格式(结构化 vs 整篇)、流式策略、prompt 模板骨架、术语注入方式、方向切换的实现、非 md 粘贴输入的结构化处理。若工单 10 的验证环境已就绪,用真实 key 抽测 2-3 种协议的可靠性再定。

## Answer

经一轮 grilling 用户全部确认(Q6 选择暂不实测,风险后置):

1. **输出协议**:`<s id="n">…</s>` / `<t id="n">…</t>` 分隔符协议为**默认**(流中凑齐一个 `</t>` 即一块完整、立即可上屏);JSON 仅作非流式可选开关。依据:BYOK 三家只有 OpenAI 有 strict schema,JSON 流式还需自建增量解析。
2. **批式请求**:3~10 块/批、约 2000 字符(按字符预算,不依赖 tokenizer);每批携带文档标题 + 上一批最后 1~2 段已译文(标注"仅上下文,勿输出")+ 术语表;`finish_reason=length` → 该批减半重试。
3. **流式与取消**:SSE + 状态机按 `</t>` 切块逐块上屏,当前块打字机预览;取消保留已完成块、未完成标"待译",批粒度断点续译。
4. **术语机制**:system prompt"必须使用"注入 + **译后程序校验自动替换**(用户选 A),被替换的块挂术语 chip 标记、用户可手改;配轻量词干匹配降低误伤。
5. **非 md 粘贴输入**:空行切段为 paragraph 块走同一管线,译文按 md 渲染;不做独立"先整理再翻译"两步 pass(需求出现再入 P2)。
6. **技术细节(打包采纳)**:Ollama 每请求显式 `num_ctx`;中→英字符预算系数 ×1.6;修复梯度:id 对齐补救 → 缺块单发 → 整批重试 → 逐块串行;译后校验块数/代码围栏数/URL 集合;prompt 骨架采用调研报告 3.1/3.2 模板(七条规则 + 术语表)。
7. **未实测**:用户暂不提供 key;协议可靠性验证后置到工单 09 原型期(届时必须真实 key,工单 10 仍开放)。
