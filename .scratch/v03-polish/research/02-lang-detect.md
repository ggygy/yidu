# 02 语言识别方案调研

> 对应 ticket:`../issues/02-lang-detect-research.md`
> 日期:2026-11-17 · 测试机:Apple M4 / Node v20.11.1
> 实测工具:`./lang-detect-bench/`(一次性脚本,不进 app/)

## 结论

- **推荐:改良启发式 v2,纯 TS、零依赖,放在前端**,替换 `app/src/languages.ts` 里的 `detectDir()`,改为返回 `{ lang, conf }`。
- 全部 106 条标注样本上,**目标语正确率**(是否该译成英文/中文)从 **75% → 95%**,**源语言正确率**从 **46% → 91%**。每次调用约 3–4 µs,所需字表约 3.6 KB。
- whatlang / lingua-rs **在本机没有实测**:没有 Rust 工具链,crates.io / static.rust-lang.org / npm / PyPI 都被代理拒绝(403),只有 GitHub 能访问。这两个库的数字取自上游 README 和精度报告,源码层面的判断是读源码推出来的,下文都有标注。
- 读源码的结论是:这两个 crate 对**纯汉字日文**都判成中文。whatlang 对**代码多的中文技术文**也没有去噪,lingua 在这类文本上没跑过。要修的几个缺陷,它们只解决「重音字母规则重叠」这一项。lingua 还要额外带上约 24 MB 模型。所以不推荐上 Rust 侧。
- 置信度:`conf < 0.6` 时仍然按结果出方向。拉丁字母低置信时目标语一定是中文,所以方向不会错。UI 上显示「自动·识别为 X」并支持一键改。具体见第 6 节。

## 3. 改良启发式设计(`lang-detect-bench/heuristic_v2.mjs`)

1. **去噪**:依次去掉围栏代码块、行内码、HTML 标签、md 链接目标、URL、email、`@scope/pkg`、路径、`--flag`、`#123`,以及标识符(camelCase、snake_case、含数字的词、`a.b`、`a::b`、`f(...)`、`T<U>`、2–6 位全大写缩写)。去完之后如果一个字母都不剩(纯代码),就退回原文。
2. **按加权比例判主脚本,不再出现一个字就定语种**:汉字、假名、谚文按 ×2.5 计,西里尔字母和拉丁字母按 ×1 计,取权重最大的一类。
3. **中/日判别**(主脚本为汉字或假名时):
   - 「」『』“”"" 引号内的内容先去掉,不参与判断(避免 `日本的「おもてなし」` 这类中文引用日文的情况)。
   - 有平假名且假名占比 ≥10% → ja;只有片假名且占比 ≥50% → ja;没有汉字只有假名 → ja。
   - 纯汉字时,若出现 **JIS X 0208 第一水准里、既不在 GB2312 也不在 Big5 的字**(日本新字体,如 駅 経 済 説 総 労 働 栃,共 325 个),满足「≥2 个」或「≥1 个且占汉字数 ≥15%」→ ja。
   - 纯汉字时,同时出现「GB2312 有而 Big5 无」和「Big5 有而 GB2312 无」的字(简繁混用,例如 `日本国憲法` 里的 国 和 憲)→ ja。
   - 其余情况判 zh,繁体中文也判 zh。
4. **拉丁语种**:每命中一个功能词(the/le/der/el…)计 2 分;变音符号加权且每种语言封顶 3 分,其中 ß、ñ、¿ 权重高,é 权重低。这样少量借词重音压不过英文功能词。全部为 0 分时默认 en,置信度低。
5. **置信度** = 主脚本占比 × 子判定置信度 × 短文本惩罚。

v1 → v2 只改了一处:日本专用字的判定限定在 JIS 第一水准。原因是 v1 把 `王喆和李堃…` 里的生僻字当成了日本字。这次修改是在**看过留出集 1 之后**做的,所以留出集 1 对 v2 已经不算干净。为此 v2 定稿后又写了留出集 2,只跑了一次。

字表可以在运行时用 `TextDecoder('gb2312' | 'big5' | 'shift_jis')` 构建,也可以预计算成静态字符串(JA_ONLY 325 字 975 B,简/繁专属 ∩ JIS1 共 880 字 2.6 KB)。两种方式在全部样本上的结果完全一致(实测,`v2 (J1-restricted tables)` 行)。**建议用静态表**:不依赖 WebView 对旧编码 TextDecoder 的支持(WKWebView、WebView2、WebKitGTK 上**均未实测**),也省掉首次约 9 ms 的构建时间。

### 4.3 v2 仍会错的情况(全部 106 条里共 10 条)

- **纯汉字日文、且不含日本专用字形**(4 条):`株式会社`、`人工知能研究所`、`国土交通省`、`名古屋市立大学` 被判成 zh,目标语会错。这几条用汉字本身就分不出来,lingua 和 whatlang 按源码同样会判成中文。eld-S 判对了其中 2 条。
- **中文提问里夹着整段英文报错**(1 条):`报错 TypeError: Cannot read properties of undefined (reading 'map') 怎么办` 被判成 en。这条的标注本身就有争议。可以考虑把 `XxxError: …` 这类报错行也当作噪声去掉,**这一条没有实现,也没有测**。
- **单个非英语问候词**(5 条):`Merci beaucoup`、`Bonjour`、`Gracias`、`Guten Morgen`、`Vielen Dank` 被判成 en。**目标语仍然正确**(都是译成中文),只是 prompt 里的源语言名写错了。接上 eld-S 兜底后,这 5 条全部修正,但会新错一条:`Hello` 被判成 es。

低于 0.6 的 9 条全是「拉丁字母、无功能词、短」的情况,其中 5 条误判,但这 9 条的目标语全部正确。阈值以上的 5 条误判是那 4 条纯汉字日文加上 TypeError 那条,当前置信度都偏高(0.77–1.0)。建议:**纯汉字、≤8 字、既无中文虚词(的了是在这们…)也无日本信号时,把置信度降到 0.5。**这样做不改变判定结果,只影响 UI 提示,**未实测**。

## 5. 放前端还是 Rust

**推荐放前端**,理由如下:

1. 现在 `auto` 就是在前端解析的(`app/src/main.tsx:~918`、`app/src/quick/main.tsx:~148`),解析完把具体方向发给 Rust,Rust 端协议不用改。
2. 启发式每次约 3 µs,同步执行,不需要 IPC 往返,输入时还能实时显示「识别为 X」。
3. 把检测挪到 Rust 的唯一收益是能直接用 whatlang/lingua,但第 2 节和第 4.3 节说明它们解决不了这次要修的核心缺陷(代码去噪、纯汉字日文),lingua 还要多带约 24 MB 模型。
4. 如果以后要在 Rust 侧做,比如命令行入口或批量翻译,这套启发式也能直接移植成 Rust:规则加 3.6 KB 静态字表,零依赖。

不推荐在前端引入 eld/franc:目标语正确率没有提升(v2 和 v2+eld-S 都是 101/106),换来的是 +60–94 KB gzip(还要离线生成 8 语子集库;完整 XS 是 272 KB gzip)和 110–163 ms 的首次加载。

## 6. 置信度阈值的行为建议

- `detectLang(text) → { lang, conf }`,`detectDir` 由它派生:zh 对应 `zh2en`,其他语言对应 `X2zh`。
- **conf ≥ 0.6**:直接使用,按钮或徽标显示「自动·日→中」这类结果。
- **conf < 0.6**:照样按判定结果发送,不打断用户。实测里低置信的全是拉丁字母情况,目标语都正确。徽标加「?」并支持一键改方向。可选做法是让源语言在 prompt 里写成通用的 "the source language",而不是错写成 English;这需要 `prompt.rs` 增加一种编码,超出本 ticket 范围,**也未验证 LLM 在源语言标错时的翻译质量是否下降**。
- 纯汉字短文本是方向风险最大的地方(会走 zh2en)。实施时应按第 4.4 节降低这类文本的置信度,并在徽标上给出「中→英(可能是日文)」的一键切换。
- 空文本或无字母时保持现状,默认 `en2zh`。

## 7. 未测项与限制

- **whatlang / lingua-rs / whichlang 都没有在本机运行**:机器上没有 cargo/rustup,static.rust-lang.org 和 crates.io 无法访问,npm(内部 Artifactory 与 registry.npmjs.org)和 PyPI 都返回 403。JS 库是从 GitHub 源码 clone 下来、手工接好依赖后跑的。lingua 和 whatlang 的数字只来自上游报告,对它们在本样本集上行为的判断只来自源码阅读。
- Rust 二进制体积的增量**没有测**。lingua 的 23.7 MB 是被嵌入的模型文件大小,不是链接后的体积。
- 样本量小(106 条)且是人工编写,百分比只用于比较方案之间的相对差距,不能当作总体精度。set1 对启发式有过拟合。
- 速度是 Node 20 / M4 上的微基准,没有在 WebView 里测。
- 旧编码 TextDecoder 在三个平台 WebView 上的支持情况**没有验证**。建议用静态字表,这样就不依赖它。
